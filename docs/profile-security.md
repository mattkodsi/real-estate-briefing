# Reader profiles

The `reader-profile` Edge Function is the only browser gateway to named reader preferences and push subscriptions. Guests stay browser-local. Profiles without a PIN are deliberately public: anyone may log in and edit them. Existing PIN-free readers cannot be given secret ownership retroactively. Four-digit PINs have low entropy; the database limits attempts across both the profile and client address (10 requests per 15 minutes). The profile cap remains effective even if a gateway address header is spoofed; confirm the gateway's `x-forwarded-for` behavior before relying on the address cap.

## API

POST JSON `{action, profile, token, ...}`. The public Supabase key may accompany the request; it is not profile authorization. `list` takes no profile/token and returns `{profiles:[{slug,name,color,hasPin}]}`. `login` takes optional `pin`; `create` takes `name,color,pin` (null means public); both return `{token,data}`. `load`, `patch` (`changes` object), and `meta` (`name,color`, optional `pin`) return `{data}` including derived `hasPin`. Omit `pin` to keep it, null to remove it, or send four digits to set it. PIN changes keep the caller's token and revoke other sessions. `subscription` takes `{sub,disabled}`; `logout` revokes this token; both return `{ok:true}`. Errors have `{error}` and HTTP 400/401/409/429/500.

Request bodies are limited to 2 MiB; regression coverage includes 800 read-history entries plus 1,200 substantial bookmarks. Preference value shapes are validated in the function and database. Larger collections receive HTTP 413 and remain unsynced until reduced.

Patch keys: saved, read, seen, learnedTerms, starEvents, theme, look, textScale, watchPlayers, notifications. Updates merge only these keys atomically in SQL. Add future preference keys to both validation layers. Subscription ownership cannot be transferred by knowing another device's endpoint; switching readers must disable/unsubscribe the previous endpoint and obtain a new endpoint, or needs an explicit authenticated transfer protocol in future.

## Migration and release

No production changes were made. Back up `prefs` and `push_subs` with service-role access before applying `202609060001_reader_profiles.sql`. It expects prefs(profile text PK, data jsonb, updated_at timestamptz), push_subs(id text PK, profile text, sub jsonb), Supabase roles, and pgcrypto in extensions. The coordinator verified this schema against the live database read-only; the migration also matches its existing defaults and NOT NULL columns. It moves legacy sha256(slug:pin) hashes into the unexposed reader_private schema and removes pinHash/pin/token from public data. Successful legacy PIN login upgrades to bcrypt (cost 10). Tokens are random 256-bit values stored only as SHA-256, expire after 30 days, and are revocable. Keep service-role keys server-side. Old browser caches may contain legacy hashes; the frontend must remove these during upgrade.

Deploy the Edge Function and coordinated frontend with migration in a maintenance window: old clients lose direct prefs/subscription access when the migration commits. Use Supabase's supported public-function configuration (JWT verification disabled for this endpoint only if required by the chosen publishable key); profile authorization is performed by this API. All other functions retain their own authorization. The migration revokes table access only for prefs/push_subs, leaves article privileges unchanged, and preserves service-role consumers. Never undo this by restoring anonymous table access; rollback should restore compatible function/frontend versions while keeping private authorization.

## Verification

Run `node --test tests/profile-server.test.mjs`. Database integration is in `tests/profile-server-db.test.sql`; run only against an empty disposable PostgreSQL database, never production. Prepare `work/profile-migration-body.sql` by removing the migration's opening `begin;` and closing `commit;`, then run `psql -v ON_ERROR_STOP=1 -f tests/profile-server-db.test.sql`. This checks actual hash migration/upgrade, private privileges, token binding/revocation, patch preservation and brute-force counters. It requires role-creation and pgcrypto permissions. These tests passed with PGlite PostgreSQL and its real pgcrypto extension. `node --test tests/profile-server*.test.mjs` also runs committed-transaction checks for persistent failed-login counters, expiration, PIN-change session revocation, and subscription ownership. The PGlite runner currently imports the isolated audit runtime at `../backend-test-runtime/node_modules`; install @electric-sql/pglite there or adapt imports to your development dependency. Production migration/deployment remains unperformed.
